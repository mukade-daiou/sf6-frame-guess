## 調査で確認した重複と対応

従来はVitestがゲームの入力・抽選・表示・採用値を検証し、`tests/*.test.mjs`が現行データと過去段階の再現を一括して検証していた。archiveは初期段階の収集・変換・採用検査を保持している。

履歴テストは同じ1298レコードを異なる時点の根拠と照合している。照合時点や承認条件が違うため、全レコードを比較するという理由だけでは削除できない。一方、技ごとに約680KBの採用判断JSONを読み直す処理や、同じキャラを何度も過去状態へ復元する処理は共通化できた。

- 6つの履歴テストで採用判断をテストファイル単位で読み込む。検査項目・出典照合・前後値の検査は残した。
- `restoreCompoundStartup`は呼び出しごとに採用判断を一度だけ読み込む。プロセスをまたぐキャッシュは設けず、再生成後の判断も読み直せる。
- held-range-reviewの復元はテスト内でキャラごとに一度にした。
- KD/HKD、additional KD、SA発生、空振り全体Fの4つの履歴比較で、投影後の全体比較に共通差分処理を使う。既存の証拠照合と許可変更数の検査を維持した。
- held-rangeの再生成テスト3本は`assertRegenerationPreserves`に統合した。生成後のJSONの意味を比較し、失敗時も含めて入力ファイルの元のバイト列を復元する。従来のテストが採用判断JSONの書式を変更していた問題も解消した。

テストの削除はしていない。重い履歴テストも通常CIの`test:data`と`test:archive`で引き続き実行する。

## 共通差分処理の仕様と使用方法

`scripts/lib/snapshot-diff.mjs`はJSONキャラクター配列を受け取り、キャラID・技ID・フィールドのパスで比較する。フレーム値に加えてinput、adoption、provenance、coverageなども対象となる。キャラ・技の配列順は対応付けに使わず、それ以外の配列は順序も比較する。

`diffSnapshots`は差分一覧を返し、`verifySnapshotDiff`は承認との照合結果を返す。`assertSnapshotDiff`は未承認差分があれば例外にする。入力は変更しない。

承認は実際の差分と同じ形式の配列で渡す。例は発生numericだけの変更であり、displayや根拠も変更する場合は、それぞれの変更を承認に記載する。

```json
[
  {
    "characterId": "ryu",
    "moveId": "example-move-id",
    "path": ["frames", "startup", "numeric"],
    "kind": "change",
    "before": 5,
    "after": 6
  }
]
```

未承認の変更・追加・削除は`unexpected`、承認と前後値が違うものは`mismatched`、実際には適用されていない承認は`unused`となる。空の承認は完全一致を要求する。重複ID・重複承認・不正な承認形式も拒否する。キャラや技全体の追加・削除は`path: []`と対象全体の前値または後値で承認し、一部だけの承認にはしない。

CLIはキャラクターデータのディレクトリ2つを比較する。対象はキャラクターJSONであり、`data/metadata.json`と生成判断の整合性は引き続き`data:check`が検査する。

```sh
npm run data:diff -- /tmp/before/characters /tmp/after/characters /tmp/approved.json
```

承認ファイルは省略でき、その場合は一切の差分を許可しない。成功は終了コード0、未承認・不一致・未使用承認は1、引数不足は2。差分を出力しても承認やデータは自動更新しない。差分一覧はレビュー用の下書きとして使い、出力をそのまま無条件に承認しない。

現行データの基準は`tests/fixtures/snapshot-approvals.json`に固定している。新しいcurrent-snapshotテストは、基準コミットと現行ディレクトリをそれぞれ独立して列挙するため、現行のファイル一覧を基準にした比較で見落としやすいキャラの追加・削除も検出する。今回の承認配列は空である。

## 検出能力の確認

既存52件のNodeテストとVitest 165件を維持したうえで、新しい差分処理に以下の変異を与えた。テスト内のコピーを変更しており、本番ファイルは書き換えていない。

| 変異・条件                                   | 検証結果                   |
| -------------------------------------------- | -------------------------- |
| フレーム値、採用状態、キャラ属性の未承認変更 | 全件拒否                   |
| 技・キャラ・フィールドの追加と削除           | 全件拒否                   |
| 承認された変更と未承認変更の混在             | 拒否                       |
| beforeまたはafterが承認と不一致              | 拒否                       |
| 未適用の承認、重複承認、重複ID               | 拒否                       |
| 正確な承認、追加・削除を含めた正確な承認     | 成功                       |
| キャラ数の変化、キャラ・技の順序変更         | 固定件数に依存せずIDで比較 |

9種類の未承認変更では、従来の投影後deepEqual方式と新共通検証がともに拒否することも確認した。共通処理は前後値を含めた承認と未使用承認を明示的に検査する。CLIも一時fixtureで未承認=1、承認済み=0、未使用承認=1、引数不足=2を確認した。

ゲームテストの抽選位置に使っていた`/ 32`はeligible.lengthへ変更し、ロスターは採用判断のID集合と照合する。SA合計はキャラ数×3レベル×3強度で検査する。過去の精査結果に対する1298件・32体などの固定値は、その時点の保存記録を検査する意味があるため残した。将来のデータ更新時に、過去履歴の投影が新しい判断を扱う対応は別途必要となる。

## 次段階で必要になること

この段階では、外部取得・更新バッチ・自動採用・本番書き込みを追加していない。次段階では取得結果を別ディレクトリに保存し、差分候補と根拠をレビューしてから承認ファイルを確定する処理を接続できる。

旧監査には段階ごとの投影と固定件数が残る。新パッチや新キャラの承認を、それぞれの過去基準へどう投影するかは履歴の要件に応じて設計する必要がある。今回すべてを単一の基準へ置き換えると段階固有の出典照合を失うため、共通差分処理の導入は4比較と現行全体保護から始めた。
